# AGX3 generic instruction encoder

`agx3_compose.c` is one table-driven encoder for every form of the three AGX3
encodings: `agx3b_tables.c` (G15, G16, G17P), `agx3c_tables.c` (G17G, G17S,
G17D, G18P) and `agx3d_tables.c` (G18G, G18M, G19P). All three come from
Apple's own llvm::AGX3 packed encoder tables, variants 0, 1 and 2. Do not
edit the tables by hand; regenerate them.

`agx3b_tables.c` / `agx3c_tables.c` were first generated by
`research/gpu/isa-re/gen-x/packgen/packgen.py` (from
`agx3{b,c}_fields_composed.json`), which is not in this tree.
`gen_agx3_tables.py` reads the same tables straight out of the Metal
toolchain and reproduces both files byte-exactly; it is what generates
`agx3d_tables.c`, and it transcribes that table into
`src/asahi/isa/AGX3d.xml` for the disassembler.

The consumer supplies Apple's anonymous field values (`fields[160]`); the
encoder gates the form on its predicates, selects each choice group, and
deposits every fixed bit and field under a shared written-bit shadow, failing
closed on any contradiction, unconsumed nonzero field, or over-wide value.
`agx3_table.py` is the same encoder in Python, plus the decoder that turns an
instruction's bytes back into a field vector.

## Regenerating

The input is Apple's `libapplegpu-nt.dylib` from Metal toolchain 27.1.266.1
(metal 32023.921), at `Metal.xctoolchain/usr/metal/32023/lib/` in the
toolchain (`xcrun -f metal-nt` points into the same toolchain). It stays out
of the tree. The table addresses in `gen_agx3_tables.py` are only valid for
that build, so the script checks the SHA-256 of the dylib's arm64 slice and
refuses any other. Write the output outside the tree and compare:

```sh
DYLIB=.../Metal.xctoolchain/usr/metal/32023/lib/libapplegpu-nt.dylib
OUT=/tmp/agx3-tables
mkdir -p $OUT
for v in b c d; do
   ./gen_agx3_tables.py tables $DYLIB $v $OUT/agx3${v}_tables.c
   cmp $OUT/agx3${v}_tables.c agx3${v}_tables.c
done
./gen_agx3_tables.py xml agx3d_tables.c $OUT/AGX3d.xml
cmp $OUT/AGX3d.xml ../../isa/AGX3d.xml
```

The G18G replay vectors need no toolchain; they are derived from the
committed witness texts in `../test/native/g18g` with the in-tree table and
XML:

```sh
../test/gen_agx3d_compose_corpus_vectors.py $OUT/vectors.c
cmp $OUT/vectors.c ../test/agx3d_compose_corpus_vectors.c
```

## Validation

`test/test-agx3-compose-corpus.c` replays 1,494 real G16G/G17S corpus
instructions (decoded by the Python composer) and 694 distinct G18G
instructions from the witness texts, and the C encoder reproduces every one
byte-exactly.

The G18G replay is a round trip through `agx3d_tables.c`: the field vectors
were decoded with the same table the encoder uses. It shows that the C
encoder, the Python decoder and Apple's bytes agree, but it cannot catch a
field-to-bit mapping that is wrong and self-consistent. The evidence for the
mapping itself is that the same extraction reproduces the independently
generated `agx3b_tables.c` and `agx3c_tables.c` byte-exactly.
